## File-by-file findings

Legend: **[CONFIRMED]** = repro'd or directly proven from code; **[PROBABLE]** = strong evidence, not fully repro'd; **[BENCHMARK-METHODOLOGY]**; **[OPTIONAL-OPT]**; **[UNVERIFIED-ASSUMPTION]**.

### `include/hydra/clock.hpp` — Group A — clean

Full read. `serialized_rdtscp()` correctly lfence-brackets `__rdtscp` (genuine serialization, not just `rdtsc`). `calibrate_ns_per_cycle()` takes two independent 1-second measurements, cross-checks <0.5% relative disagreement AND core-migration (via `rdtscp`'s own `aux` id — no extra `getcpu` syscall needed), and falls back to a `steady_clock`-based shim with a printed warning if unreliable. **No defects found.** This resolves the "is the clock methodology sound" open question from planning: it is.

Minor factual note (not a defect): calibration costs a fixed ~2 real seconds (two blocking 1s sleeps) at the start of every process that calls it — relevant to the canonical command sequence's expected runtime, not a latency concern (cold-path, once per process).

### `include/hydra/affinity.hpp` — Group A

**[CONFIRMED] Low severity, cold-path only.** Lines 24, 44, 68: `CPU_ISSET(core, &mask)`, `CPU_SET(core_id, &cpuset)`, `CPU_ISSET(expected_core_id, &actual)` each implicitly convert a signed `int` parameter to the `size_t` the glibc macros expect (`-Wsign-conversion`, reproduced via scratch strict-flags compile, Phase 0). If any of `core`/`core_id`/`expected_core_id` were ever negative, the conversion wraps to a huge `size_t` and indexes out of the fixed-size `cpu_set_t` bit array — real UB, not just a lint nit. **Currently benign**: every call site in the shipped code passes a compile-time constant (`RX_CORE_ID=4`, `MATCHING_CORE_ID=5`), and the uncommitted diff separately removes the one CLI path (`--core`) that used to let a caller-supplied `int` reach here. Fix: `static_cast<size_t>` at each site (or a `[[expects: core_id >= 0]]`-style guard) — cheap, and removes reliance on "nothing currently passes a negative value" as the only thing preventing OOB.

### `include/hydra/types.hpp` — Group A

**[CONFIRMED] struct layout is correct and verified.** `Order` (128B = 2×64B cache lines), `Level` (64B), `FillEvent` (40B) all carry `static_assert`s on `sizeof`/`alignof` that passed at compile time (Phase 0 build was clean) — the hot/cold field split in `Order` (order_id/price/qty/side/tif/prev_/next_ in the first 64B; timestamp_ns/client_id/client_tag/padding in the second) is real and matches the comment's arithmetic (22 data bytes + 26 padding + 16 pointer bytes = 64).

**[UNVERIFIED-ASSUMPTION] Medium — the optimization's own justification is explicitly unmeasured.** Lines 23-31: the comment states the hot/cold split targets "perf stat IPC shift from a ~1.2 baseline... to ~2.1... a design target and rationale, **not a measured claim**, until Phase 12 records an actually-measured number." No "Phase 12" exists anywhere in this repository (phases run 1–10; 9 is the last non-XDP correctness suite). The `ablation/flat_layout/include/hydra/types.hpp` variant exists and could A/B this, but `scripts/run_ablations.sh` (Group G/Phase 4) only harvests `median_p99_ns`/`median_p99_9_ns` from CSV — it does not capture `perf stat` IPC/cache-miss counters, so even running the existing ablation infrastructure would not validate the *specific* mechanism (IPC) claimed here, only whether end-to-end latency moves. This is exactly the class of claim the audit was commissioned to catch: a plausible, well-reasoned optimization, honestly labeled by its own authors as unproven, with the one measurement that would prove it (a `perf stat` IPC comparison, flat vs. hot/cold, under the gated benchmark) not wired up anywhere in the current tooling. Recommendation: either wire `perf stat -e instructions,cycles,cache-misses` into `run_ablations.sh` for the `flat_layout` variant specifically, or soften the comment's specific IPC numbers until that measurement exists.

Full read, extensively cross-documented (kernel/governor/SMT/NUMA preflight requirements, core-ID rationale citing this project's *specific host's* hybrid P-core/E-core topology). No defects found in the constants themselves. Flags two things to verify elsewhere, now open items for later phases:

- Pool sizes (`ORDER_POOL_SIZE=65536` etc.) claimed "sized to comfortably exceed... realistic market-data replay" — to spot-check against real exhaustion counters in Phase 4's actual benchmark run.

### `include/hydra/spsc_queue.hpp` — Group B — clean

Full read (see also direct verification during planning). Classic ever-incrementing-sequence-counter SPSC ring buffer (not the "reserve one slot" convention) — `tail - head < N` correctly uses the full capacity with no off-by-one. Memory ordering is textbook-correct and unusually well-commented: relaxed loads of the queue's *own* thread's counter (safe — self-writes are always visible to self), acquire loads of the *other* thread's counter paired with release stores (correct acquire/release handshake on both the "is there room/data" check and the "I'm done with this slot" publish). **No defects found.** `head_`/`tail_`/`buffer_` are each independently `alignas(64)`, preventing false sharing between producer- and consumer-owned cache lines.

### `include/hydra/order_book.hpp` — Group C

Full read. Core structure: `std::pmr::map`/`unordered_map` over hand-sized `monotonic_buffer_resource` arenas wrapped in `unsynchronized_pool_resource` (not a plain bump allocator) — confirmed this is the *correct* choice, not gratuitous complexity: a pure monotonic/bump arena can't reclaim space from cancelled orders during long-running continuous add/cancel churn, so the pool-resource layer on top is what makes the arena's fixed size actually sufficient over time (cancelled map/hash nodes return to the pool's free lists for reuse, not lost until process exit). `InstrumentedFallbackResource` correctly counts (via `arena_fallback_count()`) any time the arena is exhausted and the resource silently falls back to real heap allocation — good, this is exactly the "hidden heap activity" telemetry the audit asked whether the project has. **Open: is `arena_fallback_count()` ever nonzero during a real benchmark run?** — Phase 4.

**[CONFIRMED, verified correct] Positive finding — the reset()-between-trials handshake is real, provably race-free synchronization, not just "probably fine."** Traced the full chain: `matching_thread_fn` calls `sink->record(...)` (a release-store to `write_index`) strictly *after* it has finished all book/pool mutation for that order (plain program order, same thread). **[BENCHMARK-METHODOLOGY] Medium severity — no self-verification that the open-loop pacing loop stays on schedule.** `replay_phase` (lines 252-302) paces pushes against each event's `arrival_offset_ns` via a busy-wait (`while (now_ns() < target_ns) {}`) and stamps `t1_ns` (the timestamp that becomes `order.timestamp_ns`, the basis for every later latency subtraction) *after* that wait exits — i.e., at actual send time, not intended/scheduled time. ## Phase 6 — Synthesis

### Hot-path map

**Thread topology** (`src/main.cpp`, `src/pipeline.cpp`): live mode spawns `rx_thread` (self-pins `RX_CORE_ID=4`) + `matching_thread` (self-pins `MATCHING_CORE_ID=5`), sharing one `PipelineContext`. Benchmark mode pins the *calling* thread to `RX_CORE_ID` itself as producer (`benchmark.cpp:439-440`) and spawns only `matching_thread`. Both self-pinning patterns verified safe (Phase 3): `pin_to_core()`+`verify_affinity()` run before any queue/book access, and a pinning failure is always independently caught by `verify_affinity`'s own re-derivation from `sched_getaffinity()`.

**Add (GTC, rests):** producer builds `Order` → `SpscQueue::push` (`spsc_queue.hpp:48`) → `matching_thread_fn` pops via `SpscQueue::pop` (`spsc_queue.hpp:80`, `pipeline.cpp:112`) → `Matcher::match` (`matcher.hpp:54`) → `sweep_price_time`/`pro_rata_sweep` (`matcher.hpp:142`/`304`) consume any crossing liquidity → remainder (if GTC) → `OrderBook::add_order` (`order_book.hpp:52`) → `order_pool_.acquire()` (`object_pool.hpp:69`) → `find_or_create_level`→`get_or_create_level` (`order_book.hpp:270`, acquires a `Level` from `level_pool_` only on a new price) → `append_to_level` (`order_book.hpp:298`).

**Cancel:** **only reachable today via `--benchmark`'s dataset replay** (`encode_as_queue_order`, `benchmark.cpp:228-241`, explicitly builds a `qty=0` `Order` for `EventType::CANCEL`) or the deferred AF_XDP wire path. **The synthetic `rx_thread_fn` never generates a cancel** — its RNG draws `qty` from `uniform_int_distribution<uint32_t>(1,100)` (`pipeline.cpp:45,54`), always ≥1. Concretely: `test_phase7_pipeline.cpp`'s concurrent thread test uses the real `rx_thread_fn`/`matching_thread_fn` pair, so **it never exercises `matching_thread_fn`'s cancel branch under real thread concurrency either** — only `--benchmark` mode (dataset-driven, 15% cancels) does. This audit closed the resulting sanitizer-coverage gap directly (see below) rather than leaving it as a paper finding. Once reached: `matching_thread_fn` (`pipeline.cpp:123-135`) → `OrderBook::cancel_order` (`order_book.hpp:78`) → O(1) `order_index_` hash lookup → `unlink_from_level` (`order_book.hpp:315`) → `order_pool_.release()`, `level_pool_.release()` if the level just emptied.

**Match (crossing):** `Matcher::match` (`matcher.hpp:54`) dispatches on `mode_` → `sweep_price_time<false>` (FIFO, walks `Level::head_`/`Order::next_` directly — a `Matcher`-into-`OrderBook`-internals reach-in, Group C) or `pro_rata_sweep<false>`→`pro_rata_at_level` (two linear passes + one 64-bit division per eligible order, deferred-mutation pattern verified correct against `OrderBook`'s own `order_count`-gated level-freeing) → `apply_fill` (`matcher.hpp:91`, the `fill_pool_` dead-weight round-trip, finding #2) per fill → `book_.cancel_order` if a resting order is fully drained.

**Queue push/pop:** `SpscQueue::push`/`pop` (`spsc_queue.hpp:48`/`80`) — relaxed self-read + acquire-paired-with-release cross-thread handoff, verified textbook-correct (Group B, Phase 3). Both producer and consumer wrap their queue call in a `kBoundedSpinAttempts=1000` retry loop (`pipeline.cpp:61`/`108`, `benchmark.cpp:278`) — a drop-and-count on the producer side, a stop-token-responsiveness bound (not a drop) on the consumer side.

**Benchmark measurement:** `run_benchmark` (`benchmark.cpp:417`) → preflight (`run_preflight_checks`, real sysfs reads) → `calibrate_ns_per_cycle()` (assigned to `ctx.ns_per_cycle` *before* `matching_thread` is spawned — verified safe ordering, Group E) → per trial: `ctx.book/pools.reset()` (skipped trial 0; provably race-free quiescence handshake via `RawSampleSink`'s release/acquire pair, Group E) → `replay_phase` warmup then measured (open-loop-paced pushes, `t1` stamped at actual send time) → `matching_thread_fn` pops, matches, stamps `t2`/`t3`/`t4`, `sink->record(...)` → percentile computed over non-cancel samples only, median-of-5-trials reported.

**New verification performed specifically to close the cancel/sanitizer gap identified above**: ran `blitz_lob_tsan --benchmark --trials 1` and `blitz_lob_asan --benchmark --trials 1` against the real dataset (15% cancels) — **both clean, zero sanitizer reports, zero drops, zero arena fallbacks.** This is the first time in this codebase's own test suite *or* this audit that the cancel path has been exercised under real producer/consumer concurrency with ASan/TSan attached. (Latency numbers from these runs — TSan showed P99=474,178 ns, ASan P99=12,179 ns — are sanitizer-instrumentation-inflated and not meaningful as performance data; only the "zero reports" result matters here.) **[CONFIRMED] New Low-severity finding surfaced by this check**: both `blitz_lob_asan`/`blitz_lob_tsan` CSV output stamped `git=dev-build dirty=no` — factually wrong (the tree is dirty) — because, unlike `blitz_lob` and the ablation targets, neither sanitizer target's `CMakeLists.txt` block sets `HYDRA_LOB_VERSION`/`HYDRA_LOB_DIRTY` via `target_compile_definitions`, so `benchmark.cpp`'s `#ifndef` fallback (`"dev-build"`/`0`) silently applies. Not a citable-numbers path (sanitizer builds aren't meant to produce performance claims), but any provenance metadata a sanitizer-mode CSV *does* carry should be accurate. Fix: add the same two `target_compile_definitions` lines already present on `blitz_lob` to the `blitz_lob_asan`/`blitz_lob_tsan` targets.

### Benchmark discrepancy report — why different commands currently produce different results

Eight independent, concrete reasons, each with direct evidence gathered this session — none of them mysterious, all of them explain real observed number differences:

1. **Three distinct CSV-writer generations coexist in `results/`** (Group H): scaffold-era (`d976b20`, 1 comment line), an intermediate `684f9ff`-root shape (0 comment lines), and the current `write_csv_report()` shape (3-4 comment lines, env snapshot, machine-readable summary). Files from different generations were produced by different *code*, not just different runs — they are not comparable to each other or to a fresh run by construction.
2. **The published headline number matches none of them** (Group H) — likely promoted from a one-off diagnostic measurement (the "browser closed" anecdote) rather than a dedicated, saved baseline run, so there was never a controlled, repeatable command behind it in the first place.
3. **This sandbox's hardware differs from the original development machine.** This audit's own fresh runs (Phase 4), executed cleanly with 0 drops and 0 arena fallbacks, land at P99.9≈9437-9787 ns — 8x the published 1205 ns, and closer to (but still not identical to) the old `results/684f9ff/` evidence (10655-11033 ns). A virtualized/shared-resource sandbox and a dedicated, purpose-tuned host are not the same instrument, even when both pass the same preflight checks.
4. **Tree state differs across stored evidence**: `d976b20` predates the real matching engine; `684f9ff` predates the histogram removal, mandatory-dataset change, and — critically — the `reset()` cross-trial-contamination fix (Group C/E) this audit found and confirmed. Comparing across these is comparing different programs, not just different runs of one program.
5. **Sanitizer instrumentation overhead is severe and must never be mixed into a citable number.** This audit's own `blitz_lob_asan`/`blitz_lob_tsan --benchmark` runs (Phase 6 hot-path verification) landed at P99=12,179 ns / 474,178 ns respectively — 4x and 160x the Release build's number, purely from instrumentation, with no code difference. `blitz_lob_asan`/`blitz_lob_tsan` additionally mislabel their own provenance (`dev-build`/`dirty=no`, finding above) — an easy trap for anyone benchmarking the wrong binary without noticing.
6. **`--mode price_time` vs `--mode pro_rata` are different, non-interchangeable claims** (Group E) — both real, both correct, never meant to be compared as if measuring the same thing; every number in this report and the project's own docs is `price_time`-only.
7. **Trial count changes the citability contract, not just the sample size** — `--trials` below `DEFAULT_TRIAL_COUNT=5` is explicitly stamped `SMOKETEST` in both console and CSV output and should never be treated as a result (this audit's own ASan/TSan verification runs above used `--trials 1` deliberately, for exactly this reason).
8. **`scripts/run_ablations.sh` doesn't cross-check dropped-event counts** (Group G) between the runs it's comparing — two runs it presents side-by-side are only truly comparable if both actually measured the same population, which the script doesn't currently verify (this session's runs happened to all show 0 drops, so it didn't bite here, but the gap in the tooling stands).

**The fix is the same for all eight**: one canonical command sequence (below), run start-to-finish on one machine in one session, with the resulting CSVs kept as the actual cited artifact — not a number copied out of console output and then detached from the file that produced it.
