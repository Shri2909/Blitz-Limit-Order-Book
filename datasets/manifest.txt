# Dataset Manifest
# Record the blitz_gen_dataset flags used to produce any dataset referenced in
# docs/DESIGN.md benchmark numbers. The binary files are .gitignored; this file
# is the reproducibility record.
#
# WHY generated_utc/generator_version are only present on entries added from
# here on: tools/gen_dataset.cpp now prints a copy-pasteable manifest-style
# block (generation timestamp + its own HYDRA_LOB_VERSION git hash) after
# every run specifically so this file can carry that provenance going
# forward -- format_version (dataset_generator.hpp) catches a structural
# change to the binary layout, but not a silent change to the generator's
# *logic* (e.g. a distribution parameter tweak), which is exactly what a
# recorded generation timestamp + generator hash lets a future reader
# detect. The three entries below predate that instrumentation; their
# "generated" line is the file's filesystem mtime as of this note being
# written, not a value the tool itself recorded -- treat it as an
# approximate, unverified proxy, not a provenance guarantee equivalent to
# what new entries will carry.
#
# Example (current tool output format):
#   bench_110k.bin: --seed 42 --count 110000 --mid-price 100000 --spread 500
#                   --min-qty 1 --max-qty 1000 --cancel-ratio 0.15
#                   --ioc-ratio 0.05 --fok-ratio 0.02 --rate-hz 100000
#                   (generated_utc=2026-07-21T02:13:56Z generator_version=684f9ff)

bench_110k.bin: --seed 42 --count 110000 --mid-price 100000 --spread 500
                --min-qty 1 --max-qty 1000 --cancel-ratio 0.15
                --ioc-ratio 0.05 --fok-ratio 0.02 --rate-hz 100000
                (canonical dataset for docs/DESIGN.md's baseline and the
                unpinned/malloc/mutex-queue ablations -- all three of those
                ablations only change in-process code, never Order's on-disk
                byte layout, so they can replay this same file)
                (filesystem mtime as of this note: 2026-07-20T17:52:33+05:30
                -- approximate proxy only, see the WHY note above; predates
                generated_utc/generator_version instrumentation)

ablation4_flat.bin: identical flags to bench_110k.bin above (--seed 42
                --count 110000 --mid-price 100000 --spread 500 --min-qty 1
                --max-qty 1000 --cancel-ratio 0.15 --ioc-ratio 0.05
                --fok-ratio 0.02 --rate-hz 100000), but generated by
                blitz_gen_dataset_ablation_flat_layout (a build against
                ablation/flat_layout/include/hydra/{types,dataset_generator}.hpp
                -- see docs/DESIGN.md's cache-line padding section and
                scripts/run_ablations.sh, which generates this file
                automatically now) -- required because that ablation changes
                sizeof(Order), which changes DatasetRecord's on-disk size;
                replaying bench_110k.bin against an ablated build (or vice
                versa) would desync the binary record stream, not just
                latency. Same seed + config as bench_110k.bin, so the
                logical order/cancel sequence is identical -- only the
                serialized record size differs.
                (filesystem mtime as of this note: 2026-07-20T20:01:38+05:30
                -- approximate proxy only, see the WHY note above; this file
                is regenerated automatically by scripts/run_ablations.sh on
                every run, so its mtime reflects the most recent ablation
                suite invocation, not a fixed "original" generation)

matched_rate_1000hz.bin: identical flags to bench_110k.bin above except
                --rate-hz 1000 (vs. bench_110k.bin's 100000) -- used as a
                same-rate --benchmark control when diagnosing the AF_XDP
                live-pipeline latency investigation (README.md's AF_XDP
                section): isolates whether a sparse (1000/sec) arrival
                rate itself, independent of AF_XDP entirely, changes
                matching-thread behavior versus the default dense
                (100000/sec) rate.
                (filesystem mtime as of this note: 2026-07-15T10:53:27+05:30
                -- approximate proxy only, see the WHY note above)
