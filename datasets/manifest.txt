# Dataset Manifest
# Record the blitz_gen_dataset flags used to produce any dataset referenced in
# docs/DESIGN.md benchmark numbers. The binary files are .gitignored; this file
# is the reproducibility record.
#
# Example:
#   bench_110k.bin: --seed 42 --count 110000 --mid-price 100000 --spread 500
#                   --min-qty 1 --max-qty 1000 --cancel-ratio 0.15
#                   --ioc-ratio 0.05 --fok-ratio 0.02 --rate-hz 100000

bench_110k.bin: --seed 42 --count 110000 --mid-price 100000 --spread 500
                --min-qty 1 --max-qty 1000 --cancel-ratio 0.15
                --ioc-ratio 0.05 --fok-ratio 0.02 --rate-hz 100000
                (canonical dataset for docs/DESIGN.md's baseline and the
                unpinned/malloc/mutex-queue ablations -- all three of those
                ablations only change in-process code, never Order's on-disk
                byte layout, so they can replay this same file)

ablation4_flat.bin: identical flags to bench_110k.bin above (--seed 42
                --count 110000 --mid-price 100000 --spread 500 --min-qty 1
                --max-qty 1000 --cancel-ratio 0.15 --ioc-ratio 0.05
                --fok-ratio 0.02 --rate-hz 100000), but generated by a
                blitz_gen_dataset build with Order's hot/cold cache-line
                split ablated (see docs/DESIGN.md's cache-line padding
                section) -- required because that ablation changes
                sizeof(Order), which changes DatasetRecord's on-disk size;
                replaying bench_110k.bin against an ablated build (or vice
                versa) would desync the binary record stream, not just
                latency. Same seed + config as bench_110k.bin, so the
                logical order/cancel sequence is identical -- only the
                serialized record size differs.

matched_rate_1000hz.bin: identical flags to bench_110k.bin above except
                --rate-hz 1000 (vs. bench_110k.bin's 100000) -- used as a
                same-rate --benchmark control when diagnosing the AF_XDP
                live-pipeline latency investigation (README.md's AF_XDP
                section): isolates whether a sparse (1000/sec) arrival
                rate itself, independent of AF_XDP entirely, changes
                matching-thread behavior versus the default dense
                (100000/sec) rate.
