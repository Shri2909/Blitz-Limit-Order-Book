# Avellaneda-Stoikov market-maker: build plan (real-data replay)

## Context

An 8-phase Python analysis (`new-feature/DATASET_ANALYSIS.md`, `new-feature/analysis/*.py`) has already calibrated real parameters — volatility σ, fill-intensity decay k, a validated skew signal (OFI, plus a composite for two tick-constrained names), and a data-derived inventory limit — from real NASDAQ LOBSTER order-book data across 5 tickers (AAPL, AMZN, GOOG, INTC, MSFT), already downloaded to `new-feature/datasets/`. That analysis also established, with statistical rigor (HAC-corrected significance), that naive fixed-spread quoting is profitable at short horizons for 3 of the 5 names and a real, significant loss for the other 2 (INTC, MSFT) and at longer horizons for AMZN.

The next step is a working C++ Avellaneda-Stoikov strategy that trades against this project's own `OrderBook`/`Matcher` engine, backtested against a naive fixed-spread baseline — to see whether the calibrated skew (and signal) measurably improves on the naive numbers already measured.

**Explicit scoping decision (from the user directly)**: this backtest replays the **real historical LOBSTER order stream**, not a synthetic approximation. The project's existing low-latency infrastructure (`blitz_lob`, `blitz_gen_dataset`'s synthetic dataset) is untouched and out of scope — that stays exactly as it is. This feature is entirely new, lives under `new-feature/`, and touches zero existing files in `include/hydra/` or `src/`.

## What "real-data replay" means mechanically

Each LOBSTER message (`new-feature/datasets/<TICKER>_2012-06-21_message_10.csv`, columns: `time, event_type, order_id, size, price, direction`) becomes a real operation against `hydra::OrderBook`/`Matcher`:

| LOBSTER event_type | Meaning | Replay action |
|---|---|---|
| 1 (new order) | Resting limit order placed | `book.add_order(...)` — reconstructs the real historical book. **Tolerate a `nullptr` return** (pool exhaustion or duplicate order_id) the same way as the counterfactual-divergence cases below — `ORDER_POOL_SIZE` is a fixed 65,536 slots (`include/hydra/config.hpp`) while AAPL alone has 191,015 lifetime new-order events; peak *simultaneous* resting depth is almost certainly far smaller given the fast churn phase 3 measured (86-91% cancelled quickly), but this hasn't been directly checked against the real data, so the replay loop must not assume it can't happen |
| 2 (partial cancel) | Resting order's size reduced | **LOBSTER's `size` field for type-2 is the amount cancelled, NOT the resulting size** — empirically verified against the real data (e.g. order 21737116: placed with size=200, later type-2 message shows size=30, i.e. a *small trim*, not a re-quote down to 30 remaining). Must look up the order's current qty via `find_order(order_id)` **and check for `nullptr` before dereferencing** — see the counterfactual-divergence note below for why a lookup miss is expected, not a bug — then call `book.replace_order_in_place(order_id, current_qty - message_size)`. Passing the raw message field directly as `new_qty` would silently corrupt every partially-cancelled order's remaining size |
| 3 (full deletion) | Resting order removed | `book.cancel_order(order_id)` — ignore a `false` return (order not found); see counterfactual-divergence note below |
| 4 (visible execution) | A resting order was hit | Synthesize the real aggressor as an IOC order (see below), submit via `matcher.match()` — this is what lets the live `Matcher` do real price-time-priority matching, generating actual `FillEvent`s |
| 5 (hidden execution) | Hidden order executed | Not part of the displayed book at all (per LOBSTER semantics) — no `OrderBook` call, and **no signal consumes it either**: the validated trade-flow-momentum formula is lit-only (`is_lit = etypes==4` in the Python reference), and OFI/micro-price are both pure L1-book-state signals that hidden fills never touch. Read from the stream to keep it correctly synchronized with the line-aligned orderbook file, then discarded — not fed anywhere in v1 |
| 7 (halt) | Trading halt | Skip |

**The counterfactual mechanic (the one subtle, important design point)**: for a type-4 execution, the LOBSTER record tells us exactly which side traded, at what price, for what size (`direction` field: aggressor_sign = `-direction`, already established convention from the Python analysis). Replay it as a real IOC order on the aggressor's side, at that exact historical price, for that exact historical size. Submitted into the live book — which now also contains the strategy's own resting quotes — the `Matcher`'s normal price-time priority decides who actually gets filled. If the strategy's quote is better-priced than the original historical resting order at that moment, the live aggressor hits **our** quote instead (or first). If not, it falls through to the original resting order exactly as it did historically (which is only correct if that original order is still faithfully resting in our reconstructed book — guaranteed by faithfully replaying every type-1/2/3 event in order). This is the entire point of a live-insertion backtest — "what would have happened if this strategy had actually been quoting" — and it's standard methodology, not a flaw, but it needs to be **stated explicitly** in the results write-up: other historical participants' own order-submission decisions were made against a book that didn't include the strategy, so this is a first-order counterfactual, not a perfect reconstruction.

**Counterfactual divergence means later messages can legitimately reference orders that no longer exist in our book — this must be tolerated, not treated as an error.** The moment the strategy's quote intercepts a fill that historically went to a different resting order, that original order now has *less* remaining size in our reconstruction than it actually had historically (or, if fully consumed by the interception, is gone from our book entirely) — while the real LOBSTER message stream keeps referencing it by `order_id` as if nothing changed, because the messages describe what *actually* happened, not what happens in this counterfactual replay. `find_order()` returning `nullptr`, and `cancel_order()`/`replace_order_in_place()` returning `false`, are the **expected**, correct outcome for such a message once divergence has occurred — not a replay bug, and not something to log as an error or halt on. This is also exactly why the replay-fidelity check in the build order is explicitly scoped to the **no-strategy-inserted** case only: once a strategy is inserted and starts intercepting fills, the reconstructed book *should* diverge from the real orderbook CSV from that point forward, and comparing the two after that point would be comparing against the wrong ground truth, not validating anything.

**Consequence for statistical framing**: this is **one real session, one trial per ticker** — the historical sequence can't be reseeded and rerun like the previous synthetic design could. This isn't a weakness to paper over — it's exactly the same "single verified session" honesty framing `DATASET_ANALYSIS.md` already uses throughout (real host, real commit, real session, explicitly not a population claim). The backtest inherits that framing directly and consistently, which is actually a strength: the backtest's evidentiary standard matches the analysis that produced its inputs.

### Every phase-1-through-8 finding this design has to actually use, not just cite

This table exists because it's easy to build a plan that name-drops the analysis without every finding actually landing in a design decision. Each row below is a real, non-cosmetic consequence:

| Finding (phase) | Design consequence |
|---|---|
| σ needs to vary by session-phase, not be one constant (phase 4/8, ~22-39% forecast error otherwise) | `calibration.hpp` stores σ per half-hour bucket (the same 13 buckets phase 1's intraday-seasonality table already computed), not a single scalar — see `sigma_for_time()` below |
| k_bid ≠ k_ask, consistently, for every name where k is estimable (phase 2) | Strategy computes bid-side and ask-side spread halves using `k_bid`/`k_ask` separately, not one symmetric k |
| GOOG's k fails out-of-sample validation on any sub-window (phase 4, R²=−0.255) | GOOG's `k` is the full-session pooled value ONLY — `calibration.hpp` never exposes a re-fittable/rolling k for it, by construction, not by convention |
| INTC/MSFT have no viable k at all (phases 1-2, spread pinned at min tick 98.8-99.0% of session) | These two tickers get an explicit `NO_K_FALLBACK` treatment flag — see strategy design below, not a silently-undefined formula input |
| Lit-only k, not pooled with hidden fills (phase 2) | Every k value in `calibration.hpp` is the lit-only figure already |
| Order size must be per-ticker (phase 3, INTC/MSFT trade 3-15x larger clips) | `calibration.hpp` carries a per-ticker `quote_size` from median lit-fill size |
| 86-91% of real orders get cancelled before filling, median cancel time ~0-2s (phase 3) | Default `--requote-interval-ms` is explicitly set below the fastest-name median cancel time, not an arbitrary round number |
| Trade-sign autocorrelation 0.7-0.9 — fills come in runs, not independently (phase 3) | Used directly for `q_max` (already planned); **treated explicitly as a stated v2 (not v1) opportunity** for streak-aware skewing — see out-of-scope list, not silently dropped |
| OFI primary; composite (OFI+momentum+microprice) validated out-of-sample specifically for INTC/MSFT; OBI real but an order of magnitude weaker; MLOBI/queue-depletion/spread-width/VPIN/toxic-flow-by-size tested and found not to hold up (phases 5-7) | Only OFI and the INTC/MSFT composite get wired into the strategy — see the explicit "evaluated, not used" list below so every one of those six is accounted for, not silently absent |
| Fat tails, ARCH effects, Poisson-arrival violation (phases 1-2) — all caveats about a *statistical model's* assumptions | **Resolved by construction, not carried forward as a caveat**: real-data replay uses the real price path and real arrival process directly, so there's no Gaussian/Poisson assumption being imposed for these to violate |
| No fee/rebate model, no cross-asset/portfolio correlation (explicitly named as out-of-scope in the original analysis) | Inherited into this backtest's own out-of-scope list explicitly, not just implied |

|---|---|---|---|---|---|---|---|
| AAPL | 0.03528 | 0.4074 | 0.2900 | `STANDARD_K` | 15.13 | 75 | 2,634 |
| AMZN | 0.01982 | 0.3732 | 0.2931 | `STANDARD_K` | 12.85 | 60 | 2,291 |
| GOOG | 0.04026 | 0.0661 | 0.0528 | `STANDARD_K` (caveated — k does not validate out-of-sample) | 27.33 | 64 | 1,605 |
| INTC | 0.00227 | not estimable | not estimable | `NO_K_FALLBACK` | 1.01 | 100 | 5,670 |
| MSFT | 0.00262 | not estimable | not estimable | `NO_K_FALLBACK` | 1.01 | 100 | 4,508 |

The single session-level σ above is the fallback/sanity-check value; the actual `sigma_for_time()` table (13 half-hour buckets × 5 tickers = 65 values) is **not hand-transcribed into this plan** — it must be pulled directly from `new-feature/analysis/output_2026-09-01.txt`'s per-ticker "intraday seasonality" section at implementation time, to avoid a transcription error in a 65-value table nothing here would catch. Composite OLS weights for INTC/MSFT (OFI/TradeFlowMom/MicroDev) must likewise be re-extracted at full float precision from `analyze_dataset_alpha3.py`'s actual `beta` values, not the 3-decimal table in `DATASET_ANALYSIS.md` — already flagged above, restated here since this is the reference table an implementer will work from directly.

**σ must be converted to cents/√s before use in any formula, matching the int64_t-cents price convention.** The table above (and phase 1) reports σ in dollars/√s; every price/spread/skew quantity in the strategy is in cents (`Order::price`). `calibration.hpp` must store `sigma_cents_per_sqrt_s = sigma_dollars_per_sqrt_s * 100`, not the raw dollar figure — otherwise every formula that consumes σ is silently off by 100x, the same class of bug as the LOBSTER-price/100 conversion already flagged, just easier to miss because nothing crashes, the quotes are just wrong.

**γ and `skew_strength` cannot default to generic "textbook" values — verified numerically, not assumed.** A-S literature commonly uses γ on the order of 0.01–1, but that convention assumes normalized/scaled units, not real dollars-cents/real-shares/real-seconds. Checked directly: with AAPL's real σ, q_max, and a full-session T-t, γ=0.01 produces a reservation-price skew of **$767 — 5,070x AAPL's own 15.13¢ mean spread** (`q_max · γ · σ²(dollars) · T_max = 2634 · 0.01 · 0.03528² · 23400 ≈ $767`). That's not a rough edge, it's a completely broken quote (likely negative or absurdly wide).

**A second unit trap, found while deriving the "correct" γ, not before shipping it:** the reservation-price formula's output must be in **cents** (matching `Order::price`), and this project's own rule (stated above) is that σ is stored and used as `sigma_cents_per_sqrt_s`, not the raw dollar figure. That means γ **must be derived using σ in cents, not dollars** — computing it with `sigma_dollars` (as an early version of this check did) gives a γ that's too small by exactly 100² = **10,000x** once plugged into the actual cents-based formula, silently reintroducing a version of the same blown-up-quote bug this whole check exists to catch. Verified directly: AAPL's γ computed with `sigma_dollars` (≈9.9×10⁻⁷) plugged into the cents-formula produces a 75,650¢ skew against a 7.57¢ target — off by 10,000x. **The correct, cents-consistent values**: AAPL γ≈9.86×10⁻⁹, AMZN γ≈3.05×10⁻⁸, GOOG γ≈2.24×10⁻⁸, INTC γ≈7.39×10⁻⁸, MSFT γ≈6.97×10⁻⁸ (all computed to put the max-inventory, full-session skew at exactly half that ticker's own mean spread, verified self-consistent by construction). These differ across names by up to 7.5x — confirming again that **a single global `--gamma` default cannot work across the panel**; it must be a per-ticker derived value in `calibration.hpp`, with `--gamma` as a CLI *override* on top of that per-ticker default, not a replacement for having one.

Derivation formula — **σ in CENTS, this is the part that's easy to get backwards**: `gamma_default[ticker] = 0.5 * mean_spread_cents[ticker] / (q_max[ticker] * sigma_cents[ticker]^2 * T_max_seconds)`, where `sigma_cents = sigma_dollars * 100` (the same converted value `sigma_for_time()` returns, per the conversion rule two paragraphs above — reuse that conversion, don't recompute it separately). Target fraction (0.5, i.e. "half the mean spread at worst case") stated as a free, documented choice like everything else in this section — not itself derived from data, just no longer picked blind. `calibration.hpp` should include a header comment repeating this units warning verbatim, since it is exactly the kind of mistake that compiles, runs, and produces wrong numbers without any error.

The identical problem applies to `skew_strength`: OFI's raw magnitude is in **shares/second** (phase 5's own printed summary line puts AAPL's OFI std at ~460 shares/s) — applying it to a cents-denominated reservation price with `skew_strength=1.0` as a "neutral" default would shift the quote by hundreds of cents on a typical 1σ signal reading, again dwarfing a 15¢ spread. Same fix, same reasoning: `skew_strength_default[ticker] = 0.5 * mean_spread_cents[ticker] / signal_std[ticker]`, where `signal_std` is OFI's own measured standard deviation for `STANDARD_K` names (AAPL/AMZN/GOOG) or the composite score's std for `NO_K_FALLBACK` names (INTC/MSFT) — **pulled from the raw phase 5/7 output files at implementation time** (`output_alpha_2026-09-01.txt`, `output_alpha3_2026-09-01.txt`), not hand-transcribed here for the same reason the σ-bucket table isn't: five more numbers this plan hasn't independently double-checked shouldn't be typed in from memory.

## Existing APIs this reuses (confirmed exact signatures via exploration)

From `include/hydra/types.hpp`, `order_book.hpp`, `matcher.hpp`, `object_pool.hpp`:
- `Order` (128B struct), `FillEvent`, `Side`/`TimeInForce`/`OrderEventTag` enums — order IDs are caller-generated; `add_order` rejects duplicates rather than assigning IDs. **LOBSTER's own `order_id` column can be used directly as `Order::order_id`** — no separate ID-generation scheme needed for replayed orders, only for the strategy's own synthetic quote IDs (reserved disjoint range, e.g. starting at `1ULL << 62`, so they can never collide with a real LOBSTER order_id).
- `OrderBook::add_order/cancel_order/replace_order_in_place/find_order/best_bid/best_ask/best_bid_level/best_ask_level` — no pmr resource needed from the caller. `find_order(order_id)` returns `const Order*` (nullptr if not resting) — needed by the type-2 replay mapping above to read an order's current qty before reducing it.
- `Matcher::match(order, on_fill)` — `on_fill(const FillEvent&)` called synchronously, 0+ times; internally sweeps multiple price levels via real price-time priority (confirmed via `levels_consumed` tracking in `MatchStats`) — exactly what's needed for the type-4 replay mechanic. Cancels bypass `match()` — use `book.cancel_order()` directly.
- `ObjectPool<T,N>::acquire()/release()` — must be heap-allocated via `std::make_unique`.
- Construction pattern (from `src/main.cpp`): `make_unique<ObjectPool<Order,ORDER_POOL_SIZE>>()`, `make_unique<ObjectPool<Level,LEVEL_POOL_SIZE>>()`, `make_unique<OrderBook>(*order_pool,*level_pool)`, `make_unique<Matcher>(*book,mode)`.

`run_preflight_checks()` (core-pinning gate) is not reusable and not needed — this backtest validates P&L, not a latency claim.

## Component design

### 1. `lobster_replay.hpp` — the real event stream

Streams both CSVs (message + orderbook, line-aligned — confirmed convention from the Python analysis) the same way `analyze_dataset.py::stream_ticker` does, but instead of building numpy arrays, drives a live event loop: for each message row, in order, apply the operation-table mapping above, then invoke the requote callback if enough time has elapsed since the strategy's last requote (`--requote-interval-ms`, default 250ms of simulated time — see §6 for the grounding). Session boundaries (`t=34200.0` to `t=57600.0`, i.e. 09:30:00–16:00:00) come directly from the same `SESSION_START_S`/`SESSION_END_S` constants already established in `analyze_dataset.py` — used here as `T` (the A-S horizon) exactly as they were used throughout the Python analysis, for direct consistency.

A `--duration-seconds` flag can truncate replay to the first N seconds of the real session, purely as a development/iteration convenience (fast feedback while building) — the official, reported run always replays the full real session.

**Named risk: is the message file actually self-contained?** The real `<TICKER>_2012-06-21_orderbook_10.csv` is itself LOBSTER's own reconstruction, produced by replaying the message file against their engine — so if LOBSTER's continuous-session file assumes a nonempty starting book (e.g. carried over from an opening auction not represented as individual type-1 messages), a fresh, empty `OrderBook` replaying from message row 1 would diverge from their recorded L1 state immediately, before any strategy logic is even involved. This is exactly what the build-order's replay-fidelity check (no strategy inserted, compare reconstructed best bid/ask against the real orderbook CSV row-for-row) is designed to catch — if row 1 already mismatches, that's the signal, and the fix (seed initial resting orders from the real orderbook file's first row, or confirm the file is in fact self-contained) gets decided from actual evidence at that point, not guessed at now.

### 2. Live signals (`signals.hpp`)

Computed from the real replayed order flow — no synthetic proxy, no calibration-transfer risk, since this is now the same real data the Python analysis validated the signals against.

OFI: **must be read as a trailing 1-second sum, decoupled from the requote cadence** — phase 5's validated IC was computed on a 1s-bucketed grid (`analyze_dataset_alpha.py::build_grids` sums OFI events into 1-second buckets before computing IC), so "1 second of accumulated flow" is the actual unit the validated correlation numbers apply to. The default `--requote-interval-ms` is 250ms (grounded in real cancel-speed data, §6) — if OFI were instead read as "accumulated since the last 250ms tick," that's a different, unvalidated quantity at 1/4 the window, not a faithful port of the signal that was actually measured. Implementation: a small ring buffer of timestamped increments, summed over the trailing 1 second at every read, independent of how often the strategy requotes. Fires on every **replayed real book-changing event** (types 1/2/3) **and any fill against the strategy's own resting quote** (a real execution from real incoming flow, which legitimately belongs in "real market flow" even though the resting order it consumed happens to be ours) — but explicitly **excludes the strategy's own `add_order`/`cancel_order` calls during its own requoting cycle** (pure repricing, not market information; distinguished at the engine level by checking whether the affected order_id falls in the strategy's reserved ID range, e.g. `>= 1ULL<<62`, vs. the replayed-real range, e.g. `<= 287,174,077`, empirically confirmed as the real max order_id across all five tickers). Formula ported verbatim from `analyze_dataset_alpha.py::compute_ofi_events` (the exact e_bid/e_ask/OFI branches).

Micro-price deviation: pure poll from `book.best_bid_level()`/`best_ask_level()` at requote time.

Trade-flow momentum: trailing 5s sum of signed volume from the real trade tape, **lit fills only (event_type 4)** — confirmed against `analyze_dataset_alpha2.py`'s exact reference (`signed_vol[is_lit] = -directions[is_lit]*sizes[is_lit]` where `is_lit = etypes==4`; hidden/type-5 fills are excluded from this signal in the validated fit, so they must be excluded here too or the ported signal no longer matches the weights it's paired with). **Sign convention is `-direction*size`** (matches the Python reference exactly — inverted from the intuitive-looking convention, easy to flip by accident, which would silently invert the paired OLS weight).

For INTC/MSFT: fixed OLS composite weights, extracted at full float precision from the actual Python fit (not the 3-decimal-rounded markdown table, where a printed `+0.000` could hide a real small nonzero coefficient) and hardcoded as constants — reused as validated, not re-fit live in C++. This sidesteps phase 5's Pearson-vs-Spearman warning for INTC/MSFT's OFI specifically (Pearson IC there is ~2x the more trustworthy Spearman figure, inflated by a few large-magnitude outlier seconds): the actual fitted OLS regression weight already reflects the real linear relationship in the data, not a hand-picked "how strong does this correlation look" heuristic that could be misled by the same outliers — using the fitted coefficient directly, rather than inventing a weight from the correlation magnitude, is what avoids the trap that warning is about.

**Signals evaluated in the Python analysis and deliberately NOT wired into the strategy** (stated explicitly so their absence reads as a decision, not an oversight): OBI is real but an order of magnitude weaker than OFI everywhere it was measured — not wired in by default, but its computation is a straightforward addition to `signals.hpp` later if a future iteration wants it as a fallback. MLOBI (10-level imbalance), queue-depletion rate, spread-width, VPIN, and toxic-flow-by-size were all tested across phases 4, 6, and 7 and found to not hold up (wrong sign, sign-flips across session halves, or no relationship at all) — none of these five get implemented.

### 3. Strategy classes (`strategy.hpp`)

**`sigma_for_time(t)`**: not a constant lookup — indexes into the same 13 half-hour session buckets phase 1's intraday-seasonality table already computed per ticker (09:30-10:00, 10:00-10:30, ... 15:30-16:00), returning that bucket's realized σ. This directly implements the phase 4/8 finding that a session-constant σ has a real, quantified forecast error (22-39%) and that a time-of-day-conditioned σ is "the correct fix, not a re-estimation of the constant." Both the reservation-price skew term and (where applicable) the k-based spread term use `sigma_for_time(current_sim_time)`, not one static value.

**Two treatment paths per ticker, matching the calibration table's `STANDARD_K` / `NO_K_FALLBACK` flag** (this is the INTC/MSFT gap closed):

- `STANDARD_K` (AAPL, AMZN, GOOG): `r(s,q,t) = s - q·γ·σ(t)²·(T-t)`, skewed additively by the live signal (OFI, weighted by the fixed OLS-fit coefficient rather than a hand-picked correlation-magnitude heuristic — see note below on why that matters for INTC/MSFT specifically). Spread is computed **per side, asymmetrically**, using the calibrated `k_bid`/`k_ask` separately rather than one symmetric k (phase 2's finding: this asymmetry is real and consistent across every name where it's measurable) — `half_spread_bid = γσ(t)²(T-t)/2 + (1/γ)ln(1+γ/k_bid)`, `half_spread_ask` symmetric with `k_ask`. **All three names use a single full-session-pooled k (never a rolling/sub-window re-fit) — a deliberate choice for all three, not just GOOG.** Phase 2's own raw finding flagged k's session-half drift as "the strongest argument for a rolling recalibration window"; phase 4's out-of-sample walk-forward test is what actually settles it and explicitly supersedes that suggestion: AAPL/AMZN's full-session k *demonstrably generalizes* to unseen data (R²=0.70-0.81 predicting the second half from a first-half-only fit) despite drifting, so freezing it for the whole session is safe; GOOG's does not generalize at all (R²=−0.255, worse than predicting the average) — a rolling re-fit would be actively unsafe for it, not just unproven. Same operational choice (full-session k), different reasons, both grounded in the walk-forward result rather than the earlier, superseded suggestion.
- `NO_K_FALLBACK` (INTC, MSFT): no k-based spread term exists (none was ever estimable — phases 1/2 found the real spread pinned at the minimum tick 98.8-99.0% of the session). **The calibration table's ~1.01¢ "mean spread" is not itself the quoted width** — it's a time-weighted average that's slightly above 1¢ only because of the rare wider-spread moments in the other 1.0-1.2% of the session; it isn't representable in integer cents and can't be literally split in half (0.505¢ each side doesn't exist at this price granularity). The actual quoting rule is simpler and matches what the real market does 98.8-99.0% of the time: **bid and ask on adjacent integer cents** (a 1¢ total spread — `ask = bid + 1`), centered as closely as integer rounding allows on the skewed reservation price, with a **`skew_strength`-weighted reservation-price shift from the validated OLS composite signal** (OFI + trade-flow momentum + micro-price deviation) doing the directional work that the k-formula would otherwise do. This is the direct implementation of phase 7's finding for these two names: naive fixed-spread quoting loses money there, and the composite signal is the one thing shown (out-of-sample) to help.

Both paths: quote size = `calibration::quote_size[ticker]` (median lit-fill size per ticker, phase 3 — not one constant across all five names). `q_max` enforcement: once `|inventory| ≥ q_max`, suppress only the side that would grow the position further.

Requote loop: cancel both existing resting quotes, recompute, replace, every `--requote-interval-ms` (default explicitly set below the fastest-name median real cancel time from phase 3's order-lifetime table — e.g. well under ~1s — so the strategy's own requoting cadence isn't slower than what real participants actually do).

`NaiveFixedSpreadStrategy`: same requote-loop skeleton, no skew term, no signal read, no `STANDARD_K`/`NO_K_FALLBACK` branching — quotes `mid ± ticker's own measured mean-spread/2` for every name uniformly. This is deliberately the "what real naive quoting does" control that phase 8's HAC-corrected numbers already characterized economically; the whole point of the backtest is measuring whether the `STANDARD_K`/`NO_K_FALLBACK` strategy actually beats it.

Both always cancel-and-replace both sides every tick rather than diffing — avoids stale-priority bugs, and this isn't a latency benchmark.

### 4. `backtest_engine.hpp` — the unified event loop (previously under-specified — this is what actually ties everything together)

Per replayed message row, in order:
1. Apply the LOBSTER→`OrderBook` operation from the event-type table in "What real-data replay means mechanically" above (the mapping §1's `lobster_replay.hpp` is responsible for executing).
2. If the event was type 1/2/3, or a fill resulted from a type-4 event, feed the resulting L1 transition to the OFI ring buffer — using the order-id-range check (§2) to decide whether this transition originated from replayed-real activity (feed it) or from the strategy's own `add_order`/`cancel_order` calls during its last requote (exclude it). This must happen for **every** L1-changing event, not just type-4s — a type-1 new order or type-2/3 cancel changes L1 too, and OFI's formula is defined over exactly those transitions.
3. If the event was type 4, after `matcher.match()` returns, inspect the `FillEvent`(s) it generated: any whose `maker_order_id` falls in the strategy's reserved ID range gets forwarded to `strategy.on_fill()` and `markout_sink.record()`. A single historical execution can now produce fills split across the strategy's quote and the original historical resting order (the counterfactual mechanic described in "What real-data replay means mechanically" above) — both get handled, only the strategy's own portion feeds its P&L.
4. Advance simulated time to the event's timestamp. If elapsed time since the last requote exceeds `--requote-interval-ms`, invoke `strategy.on_requote_tick(sim_time, T_end)` — the cancel-both-sides/recompute/replace cycle from §3.
5. Append `(sim_time, current true mid)` to `markout_sink`'s price trace — the ground truth the post-run markout computation reads against.

Ordering matters: step 2 (OFI feed) must happen *after* step 1 (the operation is applied, so the "after" L1 state is the real post-event state) but the self-vs-real distinction in step 2 must be evaluated using the ID that *caused* the change, not the current book contents — a replayed real cancel of a real order and the strategy's own cancel of its own quote can both remove a resting order from the same price level; only the order_id tells them apart.

### 5. Markout sink — unchanged from the original design

Plain `std::vector<FillRecord>` (single-threaded, no atomics needed). Records each fill plus the real mid at fill time; post-run, computes markout at {1s, 5s, 30s} against the real replayed mid-price trace (which the engine records continuously as the real book evolves), writes CSV. HAC/significance testing stays a Python job on the emitted CSV, reusing `analyze_dataset_riskparams.py`'s already-built `newey_west_se` — not reimplemented in C++.

### 6. Backtest driver (`tools/blitz_asmm_backtest.cpp`)

Manual flag parsing matching `tools/gen_dataset.cpp`'s style. Key flags: `--ticker {AAPL|AMZN|GOOG|INTC|MSFT}`, `--strategy {as|naive|both}` (default both), `--duration-seconds` (dev convenience, default: full session), `--requote-interval-ms` (default 250 — comfortably faster than the ~1-2s median real order-cancel time phase 3 measured across every name except AAPL's near-instant p50, so the strategy's own requoting cadence isn't the bottleneck relative to real market behavior), `--gamma` (optional override; when omitted, uses the per-ticker `gamma_default` derived in `calibration.hpp` per the formula above — never a single hardcoded literature-style constant, which would be off by several orders of magnitude given these real units, see above), `--skew-strength` (same treatment — optional override, defaults to the per-ticker `skew_strength_default` derived from each signal's own measured std, not a "neutral 1.0" that would swamp the spread), `--matching-mode {price_time|pro_rata}` (default, and the **only methodologically valid choice for this specific backtest**, is `price_time` — NASDAQ is genuinely price-time priority, and the whole replay mechanic assumes the aggressor's fill gets allocated the way it actually would have been. Unlike the project's original benchmark context — where comparing price-time vs. pro-rata was a neutral engineering question about matching-engine design — using `pro_rata` here would misallocate every replayed historical execution relative to what actually happened, since real fills were never pro-rata-allocated in the first place. The flag stays available for a deliberate "what if the exchange matched differently" exploration, clearly labeled as a counterfactual-on-top-of-a-counterfactual, not a second valid backtest mode), `--output-dir`.

For a fair paired comparison, run AS and naive as **two independent replays of the identical historical stream** (fresh pools/book/matcher each, same CSV input) — the real historical flow is identical to both by construction (it's the same file), so this isolates the comparison to quoting behavior exactly the way the original synthetic design's "same seed, two books" approach did, just with a real, non-reseedable stream instead of a generated one.

Results: `results/<git-hash>/asmm_<ticker>_<strategy>.csv`, matching the existing `results/98a597b/*.csv` convention, plus a printed resolved-config/manifest-style block (matching `blitz_gen_dataset`'s pattern) and a console paired-comparison summary if both strategies ran.

**Final P&L must mark remaining inventory to market, not report cash alone.** If the strategy ends the session holding nonzero inventory, `cash_cents` by itself over- or understates real P&L depending on the sign of that inventory. The reported total P&L is `cash_cents + inventory_shares * final_true_mid_cents` (using the real mid at the session's last replayed event) — this is a mark-to-market convention, explicitly not a forced final liquidation (which would itself need a stated execution-cost assumption this analysis never calibrated). State this convention plainly in the printed summary so a reader isn't left to guess whether ending inventory was counted.

### 7. CMake + test wiring — unchanged from the original design

Append to the phase-to-exit-condition comment block in root `CMakeLists.txt`; add `blitz_asmm_backtest` (`-O2`, no `-march=native`, same reproducibility rationale as `blitz_gen_dataset`) and `blitz_lob_test_phase11_asmm` (`-O1 -g`, logic-only) targets plus `add_test(NAME phase11_asmm ...)`. No `add_subdirectory` — confirmed no such pattern exists in this project.

**Phase 11 test scope**:
1. Reservation price vs. hand-computed value for known `(s,q,γ,σ,T-t)`.
2. Optimal spread vs. hand-computed value, **both sides, using distinct k_bid/k_ask** — assert the two half-spreads are genuinely different when `k_bid≠k_ask`, not accidentally symmetric.
3. **`NO_K_FALLBACK` path** (INTC/MSFT) — assert quoting falls back to exactly a 1¢ spread on adjacent integer cents (never the non-representable 1.01¢ mean-spread figure) with no k-formula term, and that the composite signal's OLS weights are applied correctly to the reservation-price shift.
4. **`sigma_for_time()` bucket lookup** — assert it returns the correct half-hour bucket's σ at bucket boundaries and mid-bucket, not off-by-one into the adjacent bucket.
5. **OFI event increments match the Python reference** for 3-4 hand-crafted L1 transitions — highest-value test, a sign error here silently inverts the entire skew signal.
5b. **OFI's trailing-1s window is honored regardless of read frequency** — feed a scripted sequence of book events spanning >1s, read the signal multiple times at sub-second intervals (simulating 250ms requoting), assert each read reflects only the trailing 1-second sum at that moment, not "everything since the previous read" — this is what actually keeps the signal faithful to what phase 5 validated, and a plausible, easy mistake (accumulate-and-reset-on-read) would pass every other test while silently using the wrong window.
6. **LOBSTER event→OrderBook operation mapping** — feed a handful of hand-crafted message rows (one of each event type 1/2/3/4/5) through the adapter against a fresh `OrderBook`, assert the resulting book state (best bid/ask, resting order presence) matches what the real semantics require — this is now the highest-risk new component in this design and needs its own dedicated test.
6b. **Counterfactual-divergence tolerance** — feed a type-2 or type-3 message referencing an `order_id` that was never added (simulating post-divergence replay), assert the adapter does not crash (no null dereference, no unhandled `false` return) and simply continues to the next event.
7. Inventory/cash accounting against a scripted fill sequence.
8. `q_max` enforcement — bid suppressed at `≥q_max`, ask suppressed at `≤-q_max`.
9. Naive strategy stays symmetric around mid regardless of inventory, and uniformly ignores the `STANDARD_K`/`NO_K_FALLBACK` distinction (single code path for all five tickers).
10. **Per-ticker `gamma_default`/`skew_strength_default` sanity bound** — for every ticker, assert the reservation-price skew at `q=q_max, T-t=T_max` stays within a small multiple of that ticker's own mean spread (e.g. ≤2x), not the 5,070x-the-spread result a naive global constant would produce. This is the test that would have caught the gamma-magnitude bug found during planning, and it's cheap enough that skipping it isn't a real time saving.

## Explicitly out of scope for v1

1. γ sweeps/auto-tuning — `--gamma` overrides the per-ticker `gamma_default` (see the Calibration section's derivation), but no automated search across values is built; picking a different γ means re-running with a different flag.
2. Calibrating `skew_strength` from data as a real regression coefficient — no such coefficient was ever fit in the 8 completed phases (they measured correlation/IC, never a price-cents regression slope). The shipped `skew_strength_default` is magnitude-derived (scaled so a typical signal reading moves the quote a sane fraction of the spread, not an arbitrary constant), but it is still a preference knob, not a calibrated one — the distinction matters and is stated explicitly rather than blurred.
3. Live re-fitting of the INTC/MSFT composite weights — fixed constants only.
4. Multi-ticker single-run automation — one ticker per invocation; a thin wrapper script for all 5 is the natural v2.
5. Multi-day / cross-session statistical replication — inherent to real-data replay (one session = one trial); stated explicitly in results, not worked around.
6. HAC/Newey-West significance testing in C++ — stays a Python job on the emitted CSV (reuses `analyze_dataset_riskparams.py`).
7. Hawkes-process modeling of the counterfactual-insertion effect (i.e. modeling how *other* participants might have behaved differently had they seen the strategy's quotes) — the replay uses the simple, standard, stated assumption that historical order submission decisions are taken as fixed/exogenous; only fill routing reacts to the strategy's insertion.
8. **Streak-aware skewing** (widen/skew harder after N consecutive same-direction fills, not just off net inventory) — this was explicitly named as a natural next-iteration feature in phase 3 of the analysis itself ("a real design opportunity... as a follow-on"), given fills demonstrably arrive in correlated runs (trade-sign autocorrelation 0.7-0.9). `q_max` already partially compensates for this via the run-length-derived inventory cap; full streak-awareness in the quoting logic itself stays v2.
9. **Fee/rebate modeling and cross-asset/portfolio-level risk** — both were named as out-of-scope in the original 8-phase analysis (no fee data in LOBSTER, single-instrument design throughout); inherited here explicitly rather than silently assumed away a second time.
10. **OBI as a wired-in fallback signal** — real but an order of magnitude weaker than OFI everywhere measured; not part of v1's signal set (see §2), available as a cheap future addition if a later iteration wants a fallback when OFI itself is unavailable or noisy.

## Build order

1. `calibration.hpp` — extract every per-ticker constant from `DATASET_ANALYSIS.md`/raw Python outputs at full precision.
2. `lobster_replay.hpp` — build and verify in isolation first: replay a real CSV pair through a fresh `OrderBook` with **no strategy inserted at all**, and confirm the reconstructed book's `best_bid()`/`best_ask()` at each point matches the real orderbook CSV's own recorded L1 state exactly (a direct, mechanical correctness check against ground truth already sitting in `new-feature/datasets/`) — this is the highest-risk component and must be proven correct before anything else is built on it.
3. `signals.hpp` — OFI first (verify against hand-crafted transitions matching phase-11 test #3), then micro-price deviation and trade-flow momentum.
4. `markout_sink.hpp`, `strategy.hpp` (naive first, then A-S).
5. `backtest_engine.hpp` wiring replay + signals + strategy + sink together, including the requote-tick insertion and counterfactual fill routing.
6. `tools/blitz_asmm_backtest.cpp` CLI.
7. CMake wiring + `tests/test_asmm_phase11_formulas.cpp`.
8. First real run: AAPL only, `--strategy both`, full real session — inspect the paired comparison before running the full 5-ticker panel.
